Replace the synthetic curl POST with a REAL Wazuh integration:

Synthetic POST works for proving the AI pipeline. Wiring the webhook is
purely a Wazuh config edit + test. Not technically risky, just paperwork.

   - Add an <integration> block pointing at M2's wazuh-integration:8002

     /var/ossec/etc/ossec.conf

================================================================================
   PART B - WHY mitre_techniques RETURNED EMPTY
================================================================================

GOAL
----

The TriageResponse field mitre_techniques was empty in our test alerts even
though RAG was applied. Cases in TheHive should have rich MITRE tags like
mitre:T1110.001 for proper SOC categorization. Right now they just have the
category tag.


CURRENT SYMPTOMS
----------------

  rag_enrichment_applied : True
  mitre_techniques       : []   <-- expected something like [T1110.001]
  mitre_context          : empty
  kb_references          : empty
  similar_incidents      : empty


POSSIBLE ROOT CAUSES (in order of suspicion)
--------------------------------------------

1. RAG retrieves MITRE entries but they're not flowing into the LLM prompt
   - Fix: check rag-service response and confirm alert-triage uses the
     context_manager output to populate the LLM prompt

2. LLM didn't include mitre_techniques in its structured output
   - Common with smaller models (3B). The Llama 3.2 3B may be dropping
     the field if the prompt template doesn't STRONGLY ask for it.
   - Fix: check the prompt template in llm_client.py; emphasize that the
     model MUST include mitre_techniques as a list of MITRE IDs.

3. The synthetic payload doesn't have rule.mitre block, so RAG retrieval
   has nothing structured to query against
   - Real Wazuh alerts include a rule.mitre block. So this might
     "just work" once we do Part A (real Wazuh webhook).


INVESTIGATION STEPS
-------------------

1. Send a smoke test, then inspect:

     docker logs alert-triage --tail 40 | findstr -i "rag\|mitre\|context"

   Look for: "RAG retrieved N MITRE techniques: [...]"

2. If RAG retrieves but LLM doesn't include them in output, inspect the
   prompt template:

     cat services/alert-triage/llm_client.py | findstr -A 30 "PROMPT\|prompt"

   Confirm the JSON schema example in the prompt explicitly shows
   mitre_techniques as a non-empty array.

3. If RAG returns nothing, query rag-service directly:

     docker exec rag-service curl -s -X POST http://localhost:8000/retrieve `
       -H "Content-Type: application/json" `
       -d '{\"query\":\"Multiple failed RDP logins brute force\",\"top_k\":3}'

   Should return MITRE technique IDs and descriptions. If empty, the
   ChromaDB hasn't been ingested - need to run the MITRE ATT&CK STIX
   ingest into ChromaDB.


LIKELY FIX
----------

Most probable: RAG returns MITRE techniques, but the LLM (3B) is dropping
the field. Two-pronged fix:

a) Strengthen the prompt template's JSON example to show
   mitre_techniques populated with real-looking values like ["T1110.001",
   "T1078"]

b) Add a fallback: if LLM output has empty mitre_techniques but RAG
   returned techniques, populate mitre_techniques from RAG directly.
   This is more deterministic and doesn't depend on LLM compliance.

For path (b), the code change is in alert-triage's context_manager or
llm_client - take the RAG-returned techniques and ensure they end up in
TriageResponse.mitre_techniques even if the LLM omitted them.


VERIFICATION CRITERIA
---------------------

  [ ] A smoke test produces non-empty mitre_techniques in the response
  [ ] TheHive case has mitre:TXXXX tags for relevant techniques
